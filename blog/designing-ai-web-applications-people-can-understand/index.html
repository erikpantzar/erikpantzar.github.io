Designing AI web applications people can understand

Practical angles for turning powerful AI capabilities into coherent interfaces—and helping people build, test, and improve customer conversations with confidence.

01 / The starting point

Begin with the outcome someone needs

Working with AI-driven web applications means designing how people express intent, inspect decisions, and stay in control when software behaves unexpectedly.

A writing assistant, an analytical dashboard, and a customer-service agent builder all make different demands on their users. Yet each raises similar questions: What can this system do? What information is it using? What will happen if I accept its suggestion? How do I correct a mistake?

These questions become especially important when the user is configuring AI for someone else. A builder might define prompts, connect tools, and set escalation rules. A customer later experiences the result as a chat or phone call. The design must serve both the person constructing the behavior and the person affected by it.

This article focuses on that builder experience. The examples concern a fictional customer-service application for agents, communication flows, prompts, and guardrails. They are design proposals to test with users; thresholds and scenarios are illustrative, not universal operating policies.

Help people move from an intended customer outcome to a working, understandable, tested, and safely deployable AI flow.

A running example

“When a customer asks about a late delivery, identify the order, check its status, explain the next step, and hand over to a person when necessary.”

This gives the builder a purpose. The interface can then help translate that purpose into questions, tools, conditions, and fallback behavior.

02 / Foundations

Connect UX, UI, and human–computer interaction

User experience concerns the whole journey: understanding the product, completing work, recovering from problems, and returning later. The user interface supplies the controls and information through which that journey happens. Human–computer interaction provides a way to examine the relationship between human goals, system behavior, and feedback.

Nielsen’s usability heuristics offer useful starting points: make system status visible, use familiar language, support recovery, favor recognition over memory, and keep interactions consistent. These are evaluation lenses, rather than a substitute for observing actual users. [1]

  • Make state explicit. Distinguish “Saved as draft” from “Published.” Show a failed save where the person is editing.
  • Use task language. “Ask for the order number” can be a better entry point than an internal node type.
  • Support recognition. Offer a variable picker with descriptions and sample values.
  • Make recovery practical. Preserve work, provide version history, and explain what a restore affects.
  • Direct attention. Use spacing, typography, and a clear primary action to show what matters next.

For the delivery flow, ask a participant to change the handoff behavior, then explain which version customers will encounter. A polished screen that leaves that answer uncertain still has an interaction problem.

03 / Information architecture

Give people a stable model of the product

Google’s People + AI Guidebook emphasizes helping users form appropriate mental models of AI capabilities. In a builder, this also means making relationships between configurable objects understandable. [2]

Define what an agent, flow, prompt, tool, guardrail, test, and run mean in your product. Then explain ownership and reuse. A prompt embedded in one flow behaves differently from a shared prompt referenced by twenty flows.

At the point of change

Delivery response · Shared prompt
Used by three flows. Editing creates a draft. Published flows keep their current version until an update is published.

The exact model will depend on the architecture. The interface should expose its real consequences: whether changes propagate, which version is active, and where a policy applies. Useful places for this information include object headers, dependency views, and publication reviews.

04 / Human–AI interaction

Make AI behavior inspectable and correctable

Microsoft’s Human–AI Interaction guidelines address communicating capabilities and limitations, supporting correction, and responding appropriately when AI is wrong. These concerns extend familiar usability work to systems whose behavior can vary. [3]

For our delivery example, a useful execution view shows the customer input, selected flow path, tool request, tool result, policy outcome, and final response. Present recorded events as evidence. If a model generates an explanation afterward, label it as an explanation rather than treating it as a definitive account of causation.

Natural-language configuration can be an effective starting point. After someone describes a refund policy, show the resulting conditions, thresholds, permissions, and actions for review. Make assumptions and unresolved inputs visible. A conversational request should produce an editable configuration that the builder can inspect.

Also design the recovery path. If order lookup fails, does the agent ask again, retry, or hand over? The builder needs to choose and test that behavior before a customer encounters it.

05 / The working loop

Design → Test → Publish → Observe

A useful product structure separates four kinds of work while keeping movement between them easy. This is a proposed organizing model for the application, not a research standard. Tools such as Langflow demonstrate the value of a dedicated testing environment where builders can inspect outputs and tool use. [4]

  1. 1. DesignDefine the desired outcome, inputs, tool access, policies, and fallback paths. Make the draft state visible.
  2. 2. TestExercise representative and difficult scenarios. Compare observed behavior with explicit expectations.
  3. 3. PublishReview a version’s changes, test evidence, dependencies, and destination before making it live.
  4. 4. ObserveInspect real outcomes, failures, and handoffs. Turn useful findings into the next set of tests.

Test more than a successful delivery lookup. Include a missing order number, an unavailable service, an ambiguous request, an attempted policy bypass, and a customer asking for a person. Repeat important scenarios where output variability matters.

A publication summary should identify the exact version tested. “Six tests passed” means little without their scope, results, and remaining gaps. If a prompt or dependency changes afterward, indicate that the earlier evidence may no longer describe the candidate release.

Observation needs meaningful definitions. A conversation ending is not necessarily a resolved issue. Examine task completion alongside repeat contacts, handoff quality, latency, and reviewed failures. Clearly distinguish measured events from inferred outcomes. A rollback can restore configuration, but cannot undo an already issued refund or customer message.

06 / Product coherence

Standardize the way list views behave

Lists of agents, flows, prompts, and guardrails are recurring entry points. Carbon’s data-table guidance provides an established reference for organizing search, selection, row actions, batch actions, and pagination. [5]

Create one resource-list specification. Define title and creation-action placement; search, filter, and sort behavior; selection; row navigation; overflow actions; status language; and loading, empty, and error states. Keep these conventions stable while allowing useful differences in columns.

Example: the same status vocabulary across resource lists
FlowPublicationHealthUpdated
Order trackingPublished · v17Lookup failuresToday

Invoice questionsPublished · v8No issues detected3 days ago

Publication and operational health are separate dimensions: a published flow can be failing. Keep explicit text alongside any status color. Prefer a clear name link for navigation, leaving selection and row actions as separate controls.

Preserve search, filters, and position when someone returns from a detail page. Explain whether “Select all” means the visible page or every matching result. On narrow screens, retain the fields needed to identify the resource and its state; provide deliberate access to the remaining detail.

Give different empty states different next steps

“You haven’t created a flow yet” can lead to creation or a template. “No flows match these filters” should offer a way to clear them. “Flows couldn’t be loaded” needs recovery rather than a misleading empty list. Carbon’s empty-state guidance is a useful reference for these distinctions. [6]

07 / Managing complexity

Reveal detail when it becomes useful

Progressive disclosure presents the most relevant options first and makes specialized controls available when needed. It helps manage complexity without removing capability. Decide what appears first through task research rather than an assumed universal ratio of basic to advanced features. [7]

A new guardrail might initially ask what it should prevent, where it applies, and what should happen when triggered. Evaluation settings can sit in a clearly named secondary section. Keep consequential behavior visible: whether an unavailable check permits or blocks an action should never be concealed as an incidental technical detail.

Apply the same thinking to flow editing. A short sequence can work well as an ordered set of steps. A graph becomes useful when branching and relationships need spatial inspection. If both views exist, preserve the same underlying behavior and explain which structures the simpler view can represent.

Use explicit section names such as “Retry and timeout behavior.” A single “Advanced” drawer can become a second confusing form if everything accumulates inside it.

08 / Input design

Make forms support the decision

W3C’s forms guidance recommends labels, instructions, meaningful grouping, validation, and useful feedback. Placeholders cannot carry the full responsibility of labels because they disappear during input. [8]

For a prompt editor, begin with purpose and instructions. Place variables nearby, with names, types, and sample values. Group model settings and response constraints into understandable sections. Show defaults and explain their effects where they influence behavior.

Validation should describe a fix: “Choose a destination for the human handoff” is actionable. Retain the person’s input, associate the message with the relevant control, and provide a navigable error summary for longer forms. Avoid disruptive validation while someone is still composing a value.

Be precise about persistence. An autosave indicator should distinguish saving, saved, and failed states. Keep publishing a separate, understandable operation. For collaborative editing, surface conflicts and provide a way to recover competing changes.

09 / Interaction surfaces

Choose the space the task needs

Use a shared decision rule for where work happens. The following is a practical starting point to validate against task length, screen size, and user expectations.

SurfaceGood fitBuilder example
InlineA small local editRename a flow
PopoverA brief contextual choiceChoose a sort order
Side panelFocused work beside useful parent contextEdit one flow step
Modal dialogA bounded decision requiring attentionReview deletion consequences
Full pageSubstantial, resumable configurationConfigure an agent
CanvasInspecting complex relationshipsEdit branching orchestration

When a panel becomes the primary workspace on mobile, give it adequate space and a clear route back. Preserve unfinished work when moving between surfaces. Avoid making a long configuration journey depend on a stack of dialogs.

A modal also creates accessibility obligations. WAI’s dialog pattern describes moving focus inside, containing the keyboard focus sequence, offering dismissal, and returning focus appropriately when the dialog closes. A side panel needs an explicit decision about whether it is modal or leaves the parent interactive. [9]

10 / Boundaries and control

Present guardrails as understandable policies

A builder should be able to read a policy and predict its consequences. OpenAI’s practical guide to agents discusses layered guardrails and human intervention; these are useful foundations for a product that lets users configure agent behavior. [10]

Illustrative policy summary
Protect
Refunds above €500 require human approval.
When
Before the refund action executes.
Scope
Every refund tool call in this flow.
Outcome
Pause and route the request to a support agent.
On failure
Do not issue the refund; request human review.

Show whether the policy is inherited or local, what can override it, and which version is active. The approval screen should expose the proposed action, relevant evidence, and the consequences of approval or rejection.

A written instruction in a prompt does not establish an enforced permission boundary. The product should distinguish advisory behavior from checks implemented around the action itself. Let builders test both a violation and an unavailable check.

In monitoring, count triggers, blocks, escalations, and reviewed mistakes separately. Label suspected false positives until they have been assessed. Guardrail metrics should help people improve a policy, not imply that a high block count automatically means success.

11 / Conversation over time

Design voice as a timed interaction

Chat and voice can share intent, policies, and handoff logic. Voice additionally requires deliberate choices about listening, speaking, silence, interruption, recognition errors, and delays. The following recommendations extend the article’s interaction principles to that channel.

Write prompts for listening: short turns, a manageable question, and an explicit next step. Let a customer interrupt. Decide how long to wait, what to say after silence, and how to confirm information when a recognition error would change the outcome.

Example: waiting for order lookup

“I’m checking your delivery now.”

If the lookup fails: “I couldn’t retrieve the delivery status. I can connect you to a colleague.”

A voice tester should combine playback and a transcript with a timeline of speech, interruptions, tool activity, and response onset. That helps builders distinguish slow lookup from slow turn detection. Test background noise, different accents, corrections, silence, and interruptions during a long response.

Make handoff continuity part of the design: what context reaches the next person, what the customer hears while waiting, and what happens if nobody is available. Provide a text alternative where possible and make recording state and controls understandable.

12 / Inclusive interaction

Build accessibility into the shared components

WCAG 2.2 provides testable accessibility criteria. Relevant concerns include keyboard access, visible and unobscured focus, sufficient contrast, understandable inputs, alternatives to dragging, and adequately sized targets. Treat the standard as a foundation for evaluation throughout development. [11]

For an agent builder, that means offering ways to add, connect, and reorder steps without dragging. Provide meaningful control names, structural headings, and text equivalents for status. A canvas may need a complementary structured view to make relationships navigable.

Check tables, menus, and dialogs using keyboard navigation and assistive technology. Test zoom and narrow screens. Announce important asynchronous results without repeatedly interrupting someone as a generated response streams. Put these behaviors in component acceptance criteria so improvements carry across the product.

13 / Making progress

Improve one complete journey at a time

Start with a journey such as finding the delivery flow, editing a fallback, testing it, and publishing the change. Inventory the screens and states involved. Separate vocabulary and ownership problems from interaction inconsistencies and visual differences; each needs a different kind of fix.

Use that journey to establish reusable list, editor, validation, and publication patterns. Record spacing, type, color, and component states in the design system, along with behavior and content rules. Allow documented exceptions when a task genuinely needs a different treatment.

Then observe representative builders using the result. Can they find the right resource, predict the effect of a change, recover from an error, and identify the live version? Measure task success, mistakes, recovery, and time to a correctly tested flow. Use that evidence to decide what to simplify next.

Eight principles to keep close

  1. Start with the customer outcome. Organize configuration around the job to be done.
  2. Make state and scope visible. Show what is saved, tested, live, and affected.
  3. Keep common interactions consistent. Reuse behavior as carefully as visual styling.
  4. Reveal complexity deliberately. Keep consequential decisions within reach.
  5. Make generated behavior reviewable. Expose editable structure and recorded evidence.
  6. Make testing part of building. Include failure paths and version-specific results.
  7. Design correction and handoff. Give people workable recovery routes.
  8. Include everyone from the start. Build accessible interaction into shared components.
